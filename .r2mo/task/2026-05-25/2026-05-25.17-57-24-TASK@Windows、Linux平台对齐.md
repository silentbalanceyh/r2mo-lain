### P0-Critical：跨平台直接报错

#### P0-1. `cd "..." && git` execSync 模式 → 改用 `{ cwd }` 选项

**问题**：17 处 `execSync('cd "${path}" && git ...')` 在 Windows cmd.exe 下行为不一致（引号、`&&`、路径分隔符差异）。

**涉及文件**：
- `src/executor/executeMod.js` — 行 51, 52, 53, 71（4 处）
- `src/executor/executeMmr0.js` — 行 43, 44, 45, 67（4 处）
- `src/executor/executeMmr2.js` — 行 55, 56, 58, 82（4 处）
- `src/executor/executeDomain.js` — 行 62, 63, 64, 87（4 处）
- `src/executor/executeApply.js` — 行 127（1 处）

**修复步骤**：
1. 逐文件将 `execSync('cd "${repoPath}" && git xxx')` 改为 `execSync('git xxx', { cwd: repoPath, stdio: 'ignore' })`
2. 保留原有的 `stdio` 设置（部分用 `'ignore'`，部分可能未指定）
3. 若原命令有 `git fetch --all --prune && git pull` 等链式命令，拆为两次 `execSync` 调用，各自传 `cwd`

**验证**：Windows 下执行 `mxt mod` / `mxt mmr0` / `mxt mmr2` / `mxt domain` / `mxt apply` 不报 shell 语法错误。

#### P0-2. `spawn('python3')` 无 Windows 降级 → 平台判断 python / python3

**问题**：`executeDomain.js` 行 199 使用 `spawn('python3', ...)` 且可用性检查（行 320+）也只检查 `python3`，Windows 通常只有 `python`。

**涉及文件**：
- `src/executor/executeDomain.js` — 行 199（spawn）、行 326-328（可用性检查）

**修复步骤**：
1. 新增辅助函数或内联判断：`const pythonCmd = process.platform === 'win32' ? 'python' : 'python3'`
2. spawn 调用改用 `pythonCmd`
3. 可用性检查同时检测 `python` 和 `python3`，优先取可用的那个
4. 参考同项目 `executeApp.js` 行 29 的 `where/which` 模式

**验证**：Windows 下执行 `mxt domain` 能正确调用 Python。

#### P0-3. `mxt-ai-cmd.js` 硬编码 `which` → 平台感知 where/which

**问题**：行 145 `spawnSync('which', [command])` 无平台判断，Windows 上应使用 `where`。

**涉及文件**：
- `src/utils/mxt-ai-cmd.js` — 行 145

**修复步骤**：
1. 改为 `spawnSync(process.platform === 'win32' ? 'where' : 'which', [command])`
2. 与 `executeApp.js` 行 29、`executeOpen.js` 行 55 保持一致

**验证**：Windows 下 AI 命令检测不再报 `which not found`。

#### P0-4. `executeDocs.js` 行 33 硬编码 `which obsidian` → 使用标准平台模式

**问题**：在 Linux 分支内硬编码 `which`，而非使用项目统一的 `where/which` 模式。

**涉及文件**：
- `src/executor/executeDocs.js` — 行 33

**修复步骤**：
1. 在函数顶部或条件分支内使用 `process.platform === 'win32' ? 'where' : 'which'`
2. 若该行已在 `else`（非 Windows）分支内，可保留 `which` 但应加注释说明仅 Unix 分支；更好的做法是提取为统一工具函数

**验证**：`mxt docs` 在 Linux/macOS 检测 Obsidian 正常。

### P1-Medium：功能降级

#### P1-1. `mxt-audio.js` 无 Windows 播放器

**问题**：`AUDIO_PLAYERS` 列表只有 `afplay`（macOS）和 `ffplay`，缺少 Windows 原生播放器。

**涉及文件**：
- `src/utils/mxt-audio.js` — 行 6+

**修复步骤**：
1. 在 `AUDIO_PLAYERS` 中添加 Windows 条目：`{ command: 'powershell.exe', args: ['-c', '(New-Object Media.SoundPlayer "$AUDIO").PlaySync()'], platform: 'win32' }`
2. 或使用 `wmplayer` / `ffplay`（ffplay 已在列表中，可作为 Windows fallback）
3. 修改播放逻辑，按 `process.platform` 过滤可用播放器

**验证**：Windows 下 `mxt` 音频通知能播放（至少 ffplay fallback）。

#### P1-2. `install.sh` / `publish.sh` 无 Windows 等价脚本

**问题**：项目根目录只有 `.sh` 安装/发布脚本，Windows 用户需手动执行 npm 命令。

**涉及文件**：
- `install.sh`（根目录）
- `publish.sh`（根目录）

**修复步骤**：
1. 新建 `install.bat`：`@echo off && npm install -g .`
2. 新建 `publish.bat`：对应 `publish.sh` 的 npm 发布命令
3. 或改用跨平台 `node scripts/install.js` 方案（推荐长期）

**验证**：Windows 双击 `install.bat` 可全局安装。

#### P1-3. 模板中 `obsidian_askpass.sh` 不兼容 Windows

**问题**：Obsidian Git 插件的 askpass 脚本是 shell 脚本，Windows 上无法执行。

**涉及文件**：
- `src/_template/.obsidian/plugins/obsidian-git/obsidian_askpass.sh`
- `src/_template/LAIN/.obsidian/plugins/obsidian-git/obsidian_askpass.sh`

**修复步骤**：
1. 新建 `obsidian_askpass.bat` 等价脚本：`@echo off && echo %1`
2. Obsidian Git 插件本身在 Windows 上会自动选择 `.bat`，需确认插件逻辑
3. 若插件不支持自动选择，在 CLI 生成 vault 时按平台复制对应脚本

**验证**：Windows 上 Obsidian Git 插件 pull/push 不报 askpass 错误。

### 验证方式

- **单元级**：每个修复点在 Windows + Linux 分别运行对应 `mxt` 子命令
- **集成级**：完整 `mxt init` → `mxt mod` → `mxt domain` → `mxt docs` 流程在双平台跑通
- **回归**：现有 Linux/macOS 行为不变（`cd && git` → `cwd` 改写是等价变换）

### 风险与交接说明

- **风险1**：`cd && git` 拆为多次 `execSync` 后，若原命令依赖 shell 上下文（如 `git fetch && git pull` 的原子性），拆分后中间态可能不一致。但当前用法是顺序执行，无事务需求，风险极低。
- **风险2**：`python3` → `python` 降级在 Windows 上若用户装了 `python3` 命令名（如 Windows Store 版），优先级需明确。建议检测逻辑：先 `python3`，再 `python`，取第一个可用的。
- **风险3**：`obsidian_askpass.sh` 的 Windows 等价方案需与 Obsidian Git 插件版本配合，建议先验证插件是否自带 Windows 支持。
- **交接**：Plan 完成后，执行者按 P0 → P1 → P2 顺序修复，每批修复后更新 task-002.md 的 `## Changes` 章节。
